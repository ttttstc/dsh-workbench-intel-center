# 羊毛大王 · 隐式状态机清单与产品决策记录

版本：1.22.0 · 对应代码见各条 `path:line` · 结论按「UX / DX / AX」三面标注。

这份文档回答两个问题：

1. 这个工作台里到底有多少「没有写成代码的状态机」，它们各自的状态、变量、转移和失效方式是什么；
2. 对每一台，本次做了什么决定（已修 / 有意保留 / 建议后续），为什么这个决定对用户体验（UX）、开发者体验（DX）、代理体验（AX）更好。

判定标准：只要一个行为**有多个互斥状态、会被外部事件推进、且失效时用户会看到错误结果**，就算一台隐式状态机。纯渲染分支不算。

## 1. 存储层

### S1 数据文件生命周期

**状态**：不存在 → 种子初始化 → 正常读写 → 损坏。

**持有**：`dsh/store.js:40` `seedIfMissing()`、`:56` `read()`、`:74` `write()`。

**问题**：

- 损坏是「终局」：JSON 解析失败或**任何一张卡片缺标题**都让 `read()` 抛错，`GET /state` 直接 500，抓取合并也一起失败（`dsh/routes.js` 的 merge 都先 `store.read()`）。手改一次文件就能让整个工作台打不开。
- 没有任何修复入口：界面拿不到数据，也删不掉坏卡片。

**决定（已实施）**：写入仍然严格（坏数据进不了库），读取改为容错 —— `normalizeStoredState()` 丢弃无法解析的卡片并 `console.warn` 报告数量（`dsh/model.js`、`dsh/store.js`）。版本号不是 1 时告警但仍按 v1 读，不静默改写。

**理由**：UX 上「一张坏卡片 → 整个工作台白屏」是不可接受的；DX 上容错只在读侧，写入的严格校验与既有测试全部保留，不会让脏数据反向污染。

### S2 写入所有权

**状态**：三方写同一份文件 —— ① 界面整份 POST；② 抓取任务读改写；③ Agent 按提示词直接编辑文件。

**持有**：`dsh/routes.js` 的 `/state` POST、`runRadar`/`runX`、`src/shared/core.js` 的提示词。

**问题**：`normalizeState` 会把「来件里没有的榜单」重建为空（这是旧测试明确断言的行为），于是：

- 用户在抓取写入后改一条备注 → 整份旧快照盖回去，新抓的条目无声消失；
- Agent 按旧提示词模板写回（模板里只有 cards/topics）→ 三份榜单全被清空；
- 两个窗口同时编辑 → 后写者赢。

**决定（已实施）**：把所有权写成代码：卡片 / 主题 / `lastReviewedAt` 归用户，三份榜单归抓取任务与 Agent；榜单只在来件 `updatedAt` 更新时采用（`mergeState`，`dsh/model.js`）。界面 POST 会带上 `baseUpdatedAt`，服务端发现文件在期间被改过就**按 id 合并卡片**并回 `conflict: true`，界面提示「已自动合并，没有覆盖对方新增」。

**理由**：AX 上 Agent 与界面是平级写者，不能要求 Agent 理解界面的刷新时序；UX 上「我改了个备注，别人刚抓的东西没了」是最难解释的 bug。合并规则放在服务端一处，客户端与 Agent 都无需知道细节。

### S3 卡片身份

**状态**：显式 id / 位置派生 id。

**持有**：`dsh/model.js` `normalizeCard`。

**问题**：旧实现 `id || card-${index+1}`。Agent 每写回一次顺序一变，id 全变，提示词里「按 id 更新，不要改 id」形同虚设；界面上的展开态、Agent 的增量更新都会错位。

**决定（已实施）**：缺 id 时按 `标题 + 分类` 算稳定哈希；同标题同分类撞车只加 `-2` 后缀，显式重复 id 仍然报错。

**理由**：DX/AX：id 变成内容派生，重复解析同一份数据得到同一组 id；同时保留「显式重复是错误」的严格性。

### S4 字段归一化

**状态**：合法值 → 静默降级（`status`→pending、`flag`→none、`score` 夹到 1–5、非法 `verifiedAt`→空）。

**决定（保留）**：这是有意的宽松策略（Agent 写错一个字不该整份失败），但补了测试固定行为。上限不对称（卡片 >500 抛错、榜单 >500 截断）也保留：卡片是用户数据，静默丢弃更糟。

## 2. 服务端任务层

### S5 / S6 抓取任务（雷达、X）

**状态**：`idle → running → succeeded | failed`。

**旧持有**：`routes.js` 的 `xRunning` / `radarRunning` 布尔 + `lastXRun` / `lastRadarRun`（`{ok: null|true|false}`）。三个变量描述同一件事，互相能矛盾。

**问题**：

- 「在跑」只能在请求里看到，状态接口只暴露 `running`，没有进度、没有上次失败原因；
- skipped 与成功都走同一条返回路径，界面分不清；
- 进程重启后 `last*` 归零，界面以为从没跑过。

**决定（已实施）**：抽出 `dsh/jobs.js` 显式状态机（`createJob`），状态、开始/结束时间、**用时 `durationMs`**、结果（含 `bySource` 分来源条数）、错误、轮次都进快照；`/radar/status`、`/x/status` 返回 `job`，并保留旧 `last` 形状给 Agent 兼容。任务超时（默认 300s）会进 `failed` 而不是永远 `running`。

**理由**：UX 需要「在跑 / 跑完了 / 多久前跑的 / 为什么失败」这四件事；AX 需要可读的状态快照而不是猜；DX 需要能脱离网络测试的执行单元（见 `test/jobs.test.js`）。

> 1.23.0 补：这三件事以前只有一条 12 秒后自动消失的提示条。现在按钮上是「抓取中 12s…」（每秒走格，定时任务在跑也一样），
> 结束后提示条给出用时/条数/分来源，「上次刷新」下方还常驻一行结果——用户随时能确认「刚才那下到底成没成」。

### S7 浏览器补抓

**状态**：定义过 `browserFilling` + `fillFromBrowser()`，但从未被调用。

**决定（已实施）**：删除。雷达刷新本来就会内联跑一次浏览器通道，保留这段死代码只会让人以为还有「后台补入」的机制。

### S8 定时调度器

**状态**：`stopped / armed(timer)`。

**问题**：

- **小时表有两份真值**：调度器是 `[8,12,16,20]`，而 `/x/status` 返回 `hours: [9,14,21]`，界面文案又写「每天 09:00 / 14:00 / 21:00」—— 三处互相矛盾；
- 两个 `nextRunAt` 由同一个回调赋值，却分属两条接口，读起来像两套时间表；
- 插件被重复 apply 会起两个调度器 → 一天抓两遍、并发写同一份文件。

**决定（已实施）**：小时表只留 `RUN_HOURS` 一处，两个状态接口都返回它，界面按它渲染文案；同一数据目录只保留一个调度器（`schedulers` Map，重复 apply 时停掉旧的）。定时任务改为「雷达跑完再跑 X」，串行执行。

**理由**：DX —— 任何显示给用户的数字都必须来自可执行的那一份真值，否则下一个改代码的人一定会再次错过其中一处。

### S9 长任务 HTTP 等待

**状态**：请求内同步等待 / 后台任务 + 轮询。

**问题**：雷达刷新 30–60s、X 刷新 1–2min 都在请求里等完；界面只有一个「正在刷新…」，切页即失联，HTTP 层也没有超时语义。

**决定（已实施）**：`POST /radar/refresh`、`POST /x/refresh` 立刻返回 `202 + job 快照`；界面轮询状态（1.5s）直到结束，任务在后台跑时页面照常可用，切回来自动更新。同时在跑时再点返回 `200 + skipped`，不排队、不叠加。

**理由**：UX —— 长任务要能离开等待；DX —— 请求生命周期与任务生命周期解耦，测试不再需要等网络。

### S10 失败可见性

**状态**：失败 → 一句通用文案。

**问题**：`fail()` 对非校验错误只回固定兜底字符串，且不打日志。`/radar/refresh` 里一个未定义变量（`request`）导致的 `ReferenceError` 就这样被吞成「抓取羊毛雷达失败。」，并且任务根本没开始跑 —— 状态接口看起来一切正常，这个 bug 因此长期存在。

**决定（已实施）**：非校验错误回 `detail` 并 `console.error`；任务失败写进 job 的 `error`；界面区分「没开始 / 跑失败 / 跑完了」三种文案。并补了本该存在的测试（`test/refresh.test.js` 第一次请求这条路由）。

**理由**：可观测性属于 AX 与 DX 的共同底座 —— 一个不能自我报告的失败，等于没有失败。

### S11 羊毛页缓存

**状态**：空 → 新鲜（5 min）→ 过期重取，`force=1` 绕过。

**问题**：并发请求各打一次源站；重取失败时即便有旧缓存也返回 502；TTL 从「发起抓取」开始算。

**决定（已实施）**：并发请求共享同一个 in-flight Promise；重取失败时回退到旧缓存（标记 `stale`）；TTL 从抓取完成算起。

**理由**：UX —— 源站抖一下时用户看到的应该是稍旧的页面，而不是错误页。

## 3. 数据流层

### S12 雷达条目合并

**状态**：原始条目 → 关键词命中 → 分类 → 评分 → 去重 → 7 天窗口 → 上限排序。

**决定（保留）**：口径集中在 `dsh/sources.js` 的 `KEYWORDS / CATEGORIES / buildRadar`，改词表即可调整口径。补充：榜单条目 id 撞车时只留第一条（此前不查重，会让列表 key 重复）。

### S13 榜单时间轴

**状态**：`timeExact=true`（真实发布时间）/ `false`（只能算「最近活跃」）。

**决定（保留）**：NodeSeek 拿不到时间时用抓取时刻但标记 `timeExact=false`，界面显示「最近活跃」。这是诚实的降级，不要改。

### S14 核实结论

**状态**：`free / conditional / discount / unknown`。

**决定（保留）**：比「已核实/未核实」两态表达力更强。顺手修掉 `scoreWool` 里重复调用三次 `verifyFree` 的小浪费。

## 4. 客户端

### S15 标签页选择

**状态**：`radar / cards / x / wool`（1.22.0 里曾恢复出第 5 个 `linuxdo` 标签）。

**问题**：`linuxdo` 标签的两次摇摆：1.21.0 把它从 `tabDefs` 移除却留下 body / footer / 提示词（不可达分支）；1.22.0 把它恢复，结果与雷达行里的 `LINUX DO` 来源分段**重复**——同一行出现两个 linux.do 入口，用户一眼看到的就是「重复的 tab」。

**决定（已实施）**：**删除** linux.do 独立标签及其 body / footer / 抓取指令（`buildLinuxdoPrompt` 一并移除），LINUX DO 只作为雷达的一个来源存在。`state.linuxdo` 字段保留在模型里（老数据不丢、不报错），但界面不再展示。

**理由**：UX —— 同一来源不该有两个入口；DX —— 三次改动后终于只剩一条路径；数据字段保留则避免「删入口顺手删数据」。

### S16 保存管道

**状态**：`clean → dirty(700ms 防抖) → saving → saved | error`。

**问题**：失败文案写着「稍后会再试」但没有任何重试；`payload.error` 分支不可达（非 2xx 时 `apiFetch` 直接抛）；卸载时脏数据不 flush；「已保存」只在 VPS 标签页可见；没有「未保存」概念。

**决定（已实施）**：真重试（最多 2 次，线性退避）；失败文案如实说明；headers 里出现「未保存 · 重试保存」按钮；卸载时用 `sendBeacon` 补最后一次写入；成功后采用服务端合并结果；同时加 `loadSeq` 防止连点「刷新」时旧响应覆盖新数据。

**理由**：UX —— 用户必须知道「我写的东西到底存了没有」；DX —— 保存是一个有失败分支的状态机，不能只有 happy path。

### S17 提示通道

**状态**：`'' / notice / error / savedAt`。

**问题**：三个提示全部只渲染在 VPS 标签页（`cardsBody`），而雷达刷新、X 刷新、AI 抽屉的反馈都写 `notice`。默认页是雷达 → 点「刷新」零反馈；切回 VPS 才突然冒出几分钟前的过期消息。

**决定（已实施）**：`notice` / `error` 提到标签栏下方（`.intel-strip`），与当前标签页无关；成功类 12 秒自动消失，失败类常驻等用户处理。

**理由**：反馈属于「页面级」，不属于某一个 tab。这是本次 UX 收益最大的一处。

### S18 AI 抽屉 + 文件夹闸门

**状态**：`closed / gateArmed（先讲清楚再弹目录选择框）/ creating / open`。

**问题**：`folderConfirmed` 只存在组件内存；第一次点击的解释只写进 `notice`，而 `notice` 在默认页不可见 → 表现为「按钮没反应」。取消选择后按钮文案永久停在「选择资料文件夹…」。

**决定（已实施）**：提示可见（见 S17）；闸门逻辑保留（目录选择框确实需要预先解释）；文案与注释改为真实 API（`currentSession` / `newWorkspaceSession`），不再声称调用 `service.ensureSession()`。

**保留**：`folderConfirmed` 不持久化。它只是一次性解释，不是一个需要恢复的业务状态。

### S19 提示词弹窗

**状态**：`closed / open / copied`。

**问题**：三种提示词（复核、X、linux.do）共用同一个弹窗，标题恒为「复核提示词已生成」；没有 Esc/背板关闭；剪贴板不可用时 `copied` 为空，用户不知道要手点「复制提示词」。

**决定（已实施）**：按类型显示标题与说明；Esc 关闭；剪贴板不可用时明确提示手动复制。

### S20 羊毛 iframe

**状态**：`idle / loading / loaded / force-loading`。

**问题**：`woolForce` 只在 iframe `onLoad` 复位；一旦 load 事件不来，之后每次进标签页都带 `force=1` 反复回源。

**决定（已实施）**：加 10 秒兜底复位；文案从「只读嵌入」改为「隔离沙箱嵌入」（sandbox 里有 `allow-scripts`，说「只读」不准确）。

### S21 忙碌态 vs 服务端 running

**状态**：本地 `radarBusy/xBusy` × 服务端 `job.running`。

**问题**：界面只看本地请求。定时任务在跑时点刷新 → 服务端 `skipped` → 界面没有反馈；从别的窗口触发时界面完全不知道。

**决定（已实施）**：按钮的禁用与文案由 `本地 busy || 服务端 running` 决定；有任务在跑时每 4 秒轮询状态；任务结束自动重拉数据。

### S22 首屏加载

**状态**：`loading / loaded / error`。**决定（保留）**，但错误现在全局可见（S17）。

### S23 雷达筛选组

**状态**：`source × category × q × keyword × since × order`。

**问题**：两个「类别」按钮没有 `onClick`（假控件）；没有「清空筛选」；已选中的重点词在刷新后计数归零会整行消失，连「全部重点」一起消失 → 无法取消，只能刷新页面；列表**只能按时间排**，用户想先看「最值得薅的」做不到。

**决定（已实施）**：两个按钮接到真实的「全部 / 今日新增」；补「清空筛选」；已选词固定保留；新增 `order`（`羊毛分从高到低` 为默认，可切 `最新发布`），排序逻辑放进 `sortRadarItems`（`src/shared/core.js`）以便测试。

### S24 卡片筛选组

**状态**：`q / category / status / flag / minScore`。**问题**：标记筛选漏了「未标记」这一合法值。**决定（已实施）**：补上。

### S25 卡片展开

**状态**：`collapsed / expanded`（按 id）。**问题**：「今日重点」只能展开不能收起。**决定（已实施）**：改成切换。

### S26 Agent 写回契约

**状态**：Agent 相信「按 id 更新」，实际 id 不稳定、榜单会被它清空。

**决定（已实施）**：提示词统一加入「写回规则」段：只改 cards/topics/lastReviewedAt；三份榜单不要动；id 由工作台按标题+分类稳定生成；note/flag 是用户数据必须保留；能用 HTTP 就 `POST /api/intel-center/state`（服务端会校验并合并）。1.23.0 移除了 linux.do 抓取指令（来源已并入雷达）。

**理由**：AX —— Agent 需要的是**边界**，不是更多字段。把「谁能改什么」写进提示词，它的输出才可预测。

### S27 客户端与服务端的版本一致性

**状态**：`一致 / 客户端较新（服务端待重启）`。

**问题**：客户端产物打开即生效，服务端插件要等 Harness 重启才换代码。两者错位时，界面上的每个按钮都「看起来点了、实际走的是旧服务端」——这正是「刷新不知道有没有启动」的根因，而且没有任何错误可看。

**决定（已实施）**：`/meta` 返回 `apiVersion`，客户端比对 `API_VERSION`（`src/shared/core.js`），不一致就在顶部常驻横幅：**「服务端还是旧版本，请重启 Harness」**。

**理由**：UX —— 把「玄学」变成一句可执行的指示；DX —— 以后任何一次版本推进都不会再被误判为 bug。

## 5. 有意保留的「不修」

| 事项 | 为什么不改 |
|---|---|
| `version: 1` 不强制 | 只有一份历史格式，强行拒绝未知版本会让用户的数据直接打不开；现在告警并按 v1 读。 |
| 卡片上限 500 抛错、榜单上限 500 截断 | 卡片是用户数据，静默丢弃比报错更糟；榜单是抓取缓存，截断合理。 |
| 字段非法值静默降级 | Agent 写错一个枚举值不该让整份写回失败；错误从「拒绝写入」变成「降级并继续」。 |
| `folderConfirmed` 不持久化 | 一次性解释，不是需要恢复的业务状态。 |
| 雷达列表不分页 | 上限 500 条 + 关键词/来源/时间三重筛选，翻页的复杂度换不来收益。 |
| 抓取仍走本地 CDP 代理 | 这是唯一能复用用户真实登录态且不落地凭据的方式，换方案会牺牲安全边界。 |

## 6. 如果继续做（按收益排序）
1. **抓取进度**：现在只有 `running`。把「第 3/6 个关键词」写进 job，界面就能显示进度条而不是猜。
2. **失败重试策略**：单源失败目前只记录。可对直连源做一次延迟重试，并把「哪些源连续失败 N 次」展示出来。
3. **卡片删除**：界面没有删除入口（这也是卡片合并敢保留「未知 id」的前提）。加删除时应同时把 POST 语义改成显式删除指令，否则合并规则会复活已删卡片。
4. **调度器跨进程单例**：目前只保证同一进程内一个调度器；多窗口/多进程场景需要文件锁。
5. **README 与代码的数字对齐自动化**：小时表、上限条数已经集中到常量，可再加一个测试断言「README 里出现的数字等于常量」，避免第三次漂移。

## 7. 1.23.0：四条用户反馈对应的改动

用户在 1.22.0 实测后提了四条，逐条对应到状态机：

| 反馈 | 根因（状态机） | 改动 |
|---|---|---|
| linux.do 两个 tab 重复 | S15：1.22.0 恢复了独立标签，而雷达行里已有 LINUX DO 来源分段 | 删除独立标签及其 body/footer/提示词；LINUX DO 只作为雷达来源。数据字段保留不删 |
| 刷新点了不知道有没有启动 | S27 版本错位 + S5 反馈太弱 | `/meta` 返回 `apiVersion`，不一致就挂横幅；按钮显示「抓取中 12s…」；结果常驻「上次抓到 N 条 · 用时 Xs（分来源）」 |
| 排序没按羊毛分从高到低 | S23：列表被固定为时间倒序 | 新增 `order`，默认「羊毛分从高到低」（同分看时间），可切「最新发布」；逻辑进 `sortRadarItems` 并有测试 |
| X 条数太少、要按时间从近到远 | S6：上限 50 且按点赞排序 | 上限改 **200**；选择与展示都按发布时间倒序（点赞仍显示）；展示层再排一次，不依赖文件里的旧顺序 |

另外修掉一个更底层的问题：`buildRadar` 的排序比较器用「±5 分算同分」，不满足传递性（比较函数必须可传递），所以写进文件的顺序本身就是抖动的。现在改成严格全序（分数 → 时间 → 分类），并加了「换输入顺序结果不变」的测试。

一个顺带的发现：`/radar/refresh` 的真实耗时约 **20 秒**（117 条，LINUX DO 走浏览器 69 条、NodeSeek 43 条），
直连的 linux.do RSS 返回 403 后由浏览器兜住——这正是「多来源 + 单源失败不影响整体」应有的样子。
